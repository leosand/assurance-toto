# buzz-hermes-bridge

Security / correlation checkpoint between the **Buzz** workspace (collaboration, Nostr identity, approvals) and the **Hermes** runtime for the **Assurance Toto** project.

Positioning: every autonomous action of a Hermes agent that touches money, contracts or the kill-switch goes through this bridge, which applies (in order) strict schema → Nostr identity → kill-switch → business policy → idempotency → hash-chained audit → transactional Postgres effect, then replies on the Buzz channel with the same `correlation_id`.

Makes **no call to any paid API**; all data is synthetic.

## Stack

Node 20+ / TypeScript strict / Fastify / Postgres (`pg`) / Redis (`ioredis`, optional) / `nostr-tools` 2.24+ / ajv + zod.

## Installation and local validation (without Docker)

```bash
npm install
npm run build    # tsc (stdio)
npm test         # vitest: 39 tests on schema, policy (7 deny rules), idempotency, audit, killswitch, correlation
```

## Startup

```bash
# Buzz + Postgres required in prod; in demo, everything stays functional without them:
# - without BUZZ_PRIVATE_KEY → NullCollabAdapter (local capture, nothing posted)
# - without Redis → in-memory DLQ
# - without reachable Postgres → readyz=503 (pg down)
npm start
```

## Configuration (env)

| Variable | Default | Role |
|---|---|---|
| `PORT` | `3100` | Fastify HTTP |
| `DATABASE_URL` | `postgres://postgres:postgres@localhost:5432/assurance_toto` | connection |
| `REDIS_URL` | `redis://localhost:6379` | DLQ |
| `BUZZ_RELAY_URL` | `http://localhost:3000` | Buzz relay (REST `/events`, `/query`) |
| `BUZZ_PRIVATE_KEY` | *(empty → NullCollabAdapter)* | identity |
| `BRIDGE_CEOPUBKEYS` | *(empty)* | CEO npub/hex |
| `CLAIM_SETTLEMENT_THRESHOLD_EUR` | `5000` | settlement threshold |
| `BRIDGE_REQUIRE_SIGNED_COMMANDS` | *(false)* | **PROD**: CEO-only actions (reject / pricing exception / kill-switch) require a signature; otherwise `401 auth:ceo_sans_signature_valide` |
| `BRIDGE_ALLOWED_UNSIGNED_ROLES` | *(empty — no unsigned agent)* | npub/hex of Hermes agents accepted WITHOUT signature (Phase 1). **Never put a CEO npub here** — an unsigned CEO is refused (`rbac:ceo_sans_signature`), allowlisted or not |
| `APPROVAL_TTL_MINUTES` | `10080` | approvals TTL |

Never a secret in plaintext: `.env.buzz` is generated by `npm run init-buzz-keys` in mode 0600, gitignored — see `docs/keychain.md`.

## HTTP Endpoints (Fastify)

- `GET /healthz` — liveness
- `GET /readyz` — pg + adapter (+ redis if wired), `503` if any is down
- `GET /metrics` — Prometheus text (`prom-client`)
- `GET /approvals` — queue `statut='en_attente'`
- `POST /commands` — direct submission (demo/tests + Hermes callbacks)
- `POST /approvals/:correlationId/decide` — CEO decision (Nostr signature required if `event` provided)
- `POST /killswitch` — activate/deactivate (CEO only)
- `GET /dlq` — dead-letter entries
- `GET /audit/verify` — verifies the audit chain (can be slow)

## Typed commands (strict ajv schemas, `additionalProperties:false`)

- `claim.settlement.approve` `{type, claim_id, max_amount_eur, reason, approved_by, requested_at}`
- `claim.settlement.reject`
- `policy.pricing.exception.approve`
- `agent.killswitch.activate` / `agent.killswitch.deactivate`
- `finance.report.request`

**Any free-text command is rejected outright** (covered by the `rejects a free-text string` test).

## The 7 deny rules (pure policy, `src/policy/policy.ts`)

1. Author without CEO role / delegation → deny
2. Claim not found or wrong status → deny
3. `amount > allowed cap` (`CLAIM_SETTLEMENT_THRESHOLD_EUR`) → deny
4. Invalid Nostr signature → deny (verified upstream: `NIP-98` on REST, `NIP-01`+`verifyEvent` in the pipeline)
5. Identical approval already consumed (`commandes_consommees`) → deny
6. Compliance flag on the file → deny
7. Invalid schema → deny

## Agent autonomy (§6B) + anti-forgery

**Bounded autonomy on `claim.settlement.approve`** (`src/policy/policy.ts → evaluateClaimApprove`):

- `amount_eur ≤ CLAIM_SETTLEMENT_THRESHOLD_EUR`: a **claims agent** (role resolved from `BRIDGE_ALLOWED_UNSIGNED_ROLES`, unsigned event accepted in Phase 1) MAY self-settle; so may the signed CEO.
- `amount_eur > threshold`: **signed CEO only**. A claims agent is refused (`rbac:au_dessus_seuil_reserve_CEO`) and must create an `en_attente` approval via `POST /approvals` (visible on `GET /approvals` / CEO dashboard).
- Any other role (`agent-sales`, `agent-souscription`, `finance`, `conformite`, `inconnu`) is refused: `rbac:reglement_non_autorise_pour_role`.
- The other deny rules (not-found / status / cap / compliance / idempotency / schema / kill-switch) apply unchanged, whatever the amount.

**Anti-forgery** (hardening §6A):

1. An `author_pubkey` npub CEO **without a signed Nostr event** is refused on the pipeline side: `rbac:ceo_sans_signature` — the CEO identity cannot be forged by simply declaring a whitelisted npub.
2. `BRIDGE_REQUIRE_SIGNED_COMMANDS=true` (mandatory in production): CEO-reserved effect actions additionally require a verified signature (kind 9), otherwise `401 auth:ceo_sans_signature_valide`.
3. `POST /approvals` (agent → CEO escalation, §6B): the author must be a known npub (CEO or `BRIDGE_ALLOWED_UNSIGNED_ROLES`), otherwise `403 auteur_non_allowliste`. Creating a **request** does not require a signature — the decision stays CEO-signed.

`GET /approvals` exposes the `en_attente` requests; `POST /approvals` creates them (cf. repository `createApprobation`, `approbations` table in `schema_v2.sql`).

## Idempotency

`commandes_consommees.command_id` (PK) with `INSERT … ON CONFLICT DO NOTHING`. The `command_id` hash is computed on the **content** JSON of the command (not the transport id), to stay stable between the Buzz channel and the HTTP callback.

## Hash-chained audit

`audit_log.hash = sha256(prev_hash + canonicalJson(payload))`, `canonicalJson` with recursively sorted keys. `src/audit.ts → verifyAuditChain()` is called by `GET /audit/verify` and the `npm run verify-audit` script. A test pushes a falsification into the audit and checks the chain breaks.

## Kill-switch

A single `kill_switch (id=1)` row. When `actif=true`, all autonomous execution is blocked **except** `agent.killswitch.deactivate`. Covered by a test (during the lock, deactivate passes, everything else falls to `denied`).

## Correlation

`correlation_id` UUID per ingress (generated if absent). It is found consistently in:

- `audit_log.correlation_id`
- `commandes_consommees.correlation_id`
- `pnl_ledger.correlation_id`
- text of the Buzz return message + explicit `correlation_id` in the content JSON

The `correlation_id propagate` test verifies that the UUID provided at ingress ends up **unchanged** in the audit, the ledger and the Buzz message (via the `NullCollabAdapter` capture).

## Application (business effect, `settleClaimEffect`)

For `claim.settlement.approve`, in **one** Postgres transaction:

- `INSERT pnl_ledger (categorie='reglement', montant=-min(max_amount_eur, cap))`
- `UPDATE sinistres SET statut='regle'`
- `UPDATE approbations SET statut='approuve' WHERE correlation_id=…`

## DLQ

Non-retryable error (invalid signature, policy deny, business rule) → no retry, `command.dlq` audit + entry in Redis stream `dlq:commands`. Retryable error (pg/redis connection) → retried upstream (`5xx` response on HTTP, `postMessage` = throw on Buzz).

## Anti-lock-in

The pipeline only knows the `CollabAdapter` interface (`src/collab/CollabAdapter.ts`): `BuzzAdapter` (Nostr + HTTP REST to the Buzz relay) is **one** implementation. `NullCollabAdapter` (in-memory capture) is a documented fallback and lets every loop run without Buzz, reachable Postgres or Redis. Switching to another collaboration brick = reimplementing 4 methods, no policy change.

## Multi-agents

The 9 keypairs (CEO + 8 agents) are generated by `npm run init-buzz-keys`. Each Nostr keypair serves as an agent identity (npub = authority handle, nsec = secret to protect, see `docs/keychain.md`).

## What was explicitly assumed about the Buzz API (may diverge from the brief)

- REST endpoint exposed on the same host as WS (`BUZZ_RELAY_URL`): `POST /events`, `POST /query`, `POST /count`, `GET /health`, `/_liveness`, `/_readiness`.
- REST auth via header `Authorization: Nostr <base64(signed kind:27235 json)>`, tags `[u, method, payload, t]` — aligned with `nostr-tools/nip98`.
- `POST /events` response: `{"event_id","accepted","message"}`; the HTTP error is propagated as-is (`4xx/5xx`).
- The `ensureChannel` channel is a no-op: Buzz creates the channel on the fly on the first `kind:9` with the `h` tag.
- The WS subscription (NIP-01 + NIP-42) is not wired at startup (REST polling is enough for the checkpoint) — `BuzzAdapter.subscribeChannel` remains a commented extension point.
